# 错误处理与退出码契约

## 1. 体系概览

repowiki 的错误处理是一条「三异常词汇表 → 集中映射退出码 → 双格式错误输出」的单一缝：所有模块只抛 `errors.py` 定义的三个异常之一，`cli.main` 统一捕获并翻译为进程退出码，错误文案经 `output.emit_error` 按 `--json`/人读两种格式输出。整个 CLI 对使用者的契约是四个退出码：0 成功、1 校验失败/用法错误/状态损坏、2 状态冲突（任务被他人认领）、3 进展性等待（finalize 已创建 overview 任务，完成后再次运行即可）。

- 异常词汇表刻意放在叶子模块 `errors.py`（它不导入任何兄弟模块），任何命令模块都能抛错而不引入循环导入。
- 退出码映射只在 `cli.main` 一处，命令实现只负责抛异常、不自行 `sys.exit`。
- 错误输出走 `emit_error` 单一缝：JSON 契约（`ok/error/detail`）进 stdout、人读文案进 stderr，两种表示永远同步。
- 校验失败不是异常路径：`check` 把任务状态翻成 `failed` 并返回 exit 1，修复后重查即可。

## 2. 关键文件与包

- 异常词汇表
  - [src/repowiki/errors.py:13-21](file://src/repowiki/errors.py#L13-L21)：`ConflictError`（任务被其他 worker 持有等并发冲突）、`StateError`（持久化状态不可读，如 index.json 损坏——数据保全式中止）、`UsageError`（用户/输入错误，exit 1）。
- 退出码映射
  - [src/repowiki/cli.py:125-139](file://src/repowiki/cli.py#L125-L139)：`main()` 的 try/except 把三类异常翻译为 `emit_error("conflict"/"state_corrupt"/"usage", ...)` 加退出码 2/1/1；`ConflictError` 场景的约定动作是「不争抢、回 `next` 拉取」。
- 错误与结果输出缝
  - [src/repowiki/output.py:18-34](file://src/repowiki/output.py#L18-L34)：`emit()` 按 `as_json` 分流 JSON/人读两种表示；`emit_error()` 固定输出 `{"ok": false, "error": <kind>, "detail": ...}`，人读分支带 `conflict:`/`state error:`/`error:` 前缀并写 stderr。
- 异常的生产侧
  - [src/repowiki/dispatch.py](file://src/repowiki/dispatch.py)：`check` 对产出缺失/未知任务类型上抛 `UsageError`/翻 `failed`，认领冲突上抛 `ConflictError`；done 为终态，重复 check 只读不改状态。
  - [src/repowiki/state.py:24-26](file://src/repowiki/state.py#L24-L26) 与 [src/repowiki/state.py:96](file://src/repowiki/state.py#L96)：环境变量非法（如 `REPOWIKI_MAX_ATTEMPTS` 非整数）与状态文件损坏（`load()` 解析失败）是 `UsageError`/`StateError` 的典型生产点； exhausted 毒任务在未加 `--force` 时以 `ConflictError` 拒绝重置。

## 3. 架构与设计约定

- 异常词汇表必须是叶子模块：`errors.py` 的 docstring 明示「Lives in a leaf module on purpose」——把异常下沉到零依赖模块，换取命令模块抛错时的零导入成本。
- 退出码是唯一进程级契约：`0/1/2/3` 各有明确语义且 3 特意不是错误（finalize 的两步协议依赖它）；映射集中在 `cli.main`，禁止在命令实现里散落 `sys.exit`。
- 数据保全优先于静默恢复：`StateError` 的语义是「保留现场的中止」——`state/index.json` 或 `catalog.json` 损坏时报错退出，绝不静默清空任务清单；显式恢复路径只有 `plan --replan --force`。
- 双格式同步：`emit` 的 docstring 点明单一缝的价值——「a new field lands in both or neither」，JSON 字段与人读文案不允许单边演化。
- 校验失败走状态机而非异常：`check` 的语义缺陷判定把任务翻 `failed`（attempts+1），连续 3 次到达上限后进入 exhausted，需人工 `release --task <id> --force`。

## 4. 开发者应遵循的规则

1. 新增命令不得自定义退出码或直接 `sys.exit`：抛 `errors.py` 三异常之一，映射由 `cli.main` 统一处理；确需新语义先扩词汇表与映射，再写命令。
2. 错误分类对号入座——用户输入/用法问题抛 `UsageError`；持久化状态不可读抛 `StateError`（且不得顺手清理现场）；并发/认领冲突抛 `ConflictError`（调用方约定动作是重试或回队列，不是强制覆盖）。
3. 一切命令输出（正常结果与错误）必须经 `emit`/`emit_error` 输出：新增返回字段时 JSON 与人读文案同步增补，禁止绕过输出缝直接 `print`。
4. 遇到 exit 2（他人认领/状态冲突）不要 `--force` 争抢：回 `next` 拉取新任务，或等过期回收；exhausted 任务的 `--force` 重置是人工决策。
5. 遇到 exit 3 按「进展性等待」处理（如 finalize 先创建 overview 任务后再次运行），不要当失败上抛。
